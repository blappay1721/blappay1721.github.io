Persona chatbot and Discord bot platform

A fine-tuned 1.7B model that replies in each friend's own voice

330kmessages from 8 years of chat
  • Built the training data from 330,000 Discord messages: scrubbed personal info (emails, phone numbers, IPs, keys), mapped alt accounts to one person, merged rapid-fire bursts into single turns, and split the history into 16,581 conversations at 45-minute gaps.
  • Fine-tuned Qwen3-1.7B with QLoRA on a 12 GB RTX 3060: 64,000 reply examples across 36 personas, then a DPO pass on 21,000 preference pairs that ships only if it beats the SFT model on held-out conversations. Quantized to 4-bit GGUF and served locally with Ollama.
  • Dual-index RAG: each reply gets 3 of the persona's own past lines for voice (from 156,000) and, only when confidently relevant, 2 snippets of past conversations for facts (from 39,000). A persona only "remembers" DMs they were in.
  • Evaluation showed factual recall was the weak point, so a rebuild around extracted and verified facts is in progress.
  • In Discord, /chat opens a channel where the persona posts under their own name and avatar via webhooks; public chats queue up to 5 people and answer each in turn. The bot runs over Discord's gateway, so it needs no public URL or open ports.

Python, PyTorch, Hugging Face (TRL, PEFT), llama.cpp, Ollama, Node.js, discord.js · Bot code · Model and data pipeline private (built on friends' messages)

Self-hosted game server platform

Containerized Minecraft network on a 16 GB mini PC

30+unique users
  • In one day, moved a Velocity proxy and three Paper servers from hand-run tmux sessions to Docker containers managed by Pelican, one server at a time from a written runbook, with no data lost, and added a limbo fallback that holds players while the hub restarts. A cutover script checks preconditions, takes a fresh backup, copies the data, repoints the proxy and keeps the old copy until I confirm, so every move can be rolled back.
  • The two large worlds start on demand: a player who asks for one waits on the hub with a countdown, about 1 min 50 s from a cold start with 57 plugins, and each world stops about 11 minutes after its last player leaves. The proxy plugin that does this uses a service account that can only start and stop those two servers. That frees about 7.5 GB of the 16 GB while nobody is playing, on a box that also runs my Discord bot's LLM.
  • Hourly encrypted restic snapshots, 30–110 MB of new data each, go to a local repository and queue to an append-only one on another machine over Tailscale, so a compromised server can add snapshots there but not delete them. The job pauses world saves through the panel's API with a service account that can only send console commands, copies live SQLite databases with VACUUM INTO, and has passed a restore test.
  • No admin ports open to the internet: collaborators use the web panel through a Cloudflare Tunnel, with 2FA and per-server permissions instead of SSH, SFTP and dashboards are reachable only over Tailscale, and backends listen only on the Docker bridge. Players join by domain through an SRV record. Moved fail2ban's bans into Docker's DOCKER-USER chain after finding that ufw rules never reach container ports, and rewrote a jail filter to catch slow read-timeout bot scanners.
  • Split the 1 TB NVMe into LVM volumes for game data, backups, metrics and databases, and cleared 32 GB of redundant plugin archives. Per-container memory and CPU limits, zram swap, and JVM flags that return idle heap to the OS keep the network and the LLM within 16 GB, watched in Grafana.
  • Traced NVMe controller resets and a watchdog crash to a firmware power-state (APST) bug, fixed with a kernel boot parameter, and mass player disconnects to Wi-Fi power management and mesh roaming, fixed persistently in NetworkManager.
